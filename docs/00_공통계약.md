# StudySpot 공통 개발 계약

## 문서 상태와 사용 방법

참조: 사용자가 제공한 팀 브랜치·폴더 구조 및 「LangChain」 대화의 공통 개발 규격. 역할 번호는 이번 요청의 1~6번을 따른다. 과거 답변의 다른 폴더 구조 대신 최신 `StudySpot/` 구조를 적용한다. `만두스크림.docx` 원문을 이번 작업에서 직접 검증한 문서는 아니다.

**기존 합의**는 유지한다. 아래 **추가 제안**은 불명확한 경계를 해결하기 위한 설계안이며, 이미 팀이 승인한 규격으로 간주하지 않는다. skeleton PR에서 관련 담당자가 확정한 뒤 구현한다. 이 문서는 구현 완료를 의미하지 않는다.

각 팀원에게 본 문서와 본인 역할 명세서를 함께 전달한다. 문서 간 충돌 시 기존 사용자 합의를 우선하고, 새 결정은 본 문서에 먼저 반영한다.

## 1. 기존 합의

- Python + LangChain. 서울 내 API 지원 상권 5~10곳에서 스터디카페 출점 후보를 최대 3곳 추천한다. 적합 후보가 부족하면 개수를 채우기 위해 만들지 않는다.
- 필수 조건: 희망 지역, 보증금·월세 예산, 타깃 연령, 운영 시작·종료 시간.
- LLM은 조건 확인·계획·Tool 선택·해석을 담당한다. 조회는 데이터 Tool, 모든 점수 계산은 `calculate_market_score`만 담당한다.
- 데이터 없음과 실제 0을 구분한다. 누락은 `missing_data`, Mock은 `is_mock=True`로 표시한다.
- 보고서 전송·현장답사 일정 생성은 실행 내용을 보여주고 사용자 승인 후 실행한다.
- 모든 Tool은 `ToolResult`를 반환한다. 일반 내부 함수까지 Tool로 만들거나 같은 반환형을 강제하지 않는다.
- 단위 테스트는 각 담당자가 작성한다. UI 담당자는 전체 통합 테스트를 담당한다.

## 2. 소유권과 브랜치

| 역할 | 브랜치 | 단독 수정 파일 |
|---|---|---|
| 1 API · 중우 | `feature/api-tools` | `tools/academy_tools.py`, `tools/subway_tools.py`, API 전용 테스트·fixture |
| 2 Memory · 소유 | `feature/memory` | `memory/store.py`, 제안 추가 `memory/state.py`, Memory 테스트 |
| 3 Guardrail · 연주 | `feature/guardrails` | `middleware/guardrails.py`, `middleware/middleware.py`, 오류 테스트 |
| 4 점수·모델 · 효주 | `feature/scoring` | `models/schemas.py`, `tools/scoring_tools.py`, 모델·점수 테스트 |
| 5 구조·Agent · 석휘 | `feature/agent-core` | `agent/main_agent.py`, `agent/prompts.py`, `docs/설계서.md`, 구조·공통 설정 파일 |
| 6 UI · 명하 | `feature/ui` | `app.py`, UI·통합 테스트 |

Memory 모델의 의미·수명은 역할 2가 설계하고 역할 4가 `models/schemas.py`에 선언한다. 역할 2는 `memory/state.py`에서 상태 갱신·요약·체크포인트 연결을 개발한다. Guardrail 정책은 `guardrails.py`, 실행 훅·재시도 연결은 `middleware.py`에 둔다.

**추가 제안 — 미배정 업무:** `tools/market_tools.py`의 지원 상권 검색·식별자 해석·혼잡도·방문자·경쟁·임대료 조회와 제안 추가 `tools/action_tools.py`의 전송·일정 실행은 역할 5가 인터페이스 및 통합 책임을 맡는다. 실 API 구현은 별도 배정 전까지 보류하며 계약에 맞는 명시적 Mock으로 통합한다. 역할 1에게 SK 외 전체 조회를 암묵적으로 넘기지 않는다. 실제 외부 행동 미구현 시 실행 성공이라고 표시하지 않는다.

## 3. 공통 모델: `models/schemas.py`

아래는 선언 명세다. 구현 알고리즘이나 라이브러리별 실행 코드는 포함하지 않는다. 공통 모델은 한 번만 선언하고 모두 import한다. 목록·사전 기본값은 인스턴스마다 독립 생성한다.

| 모델 | 필드·타입 계약 |
|---|---|
| `ToolResult` | `success: bool`, `source: str`, `data: dict[str, Any] \| list[Any]`, `error_code: str \| None`, `error_message: str \| None`, `is_mock: bool` |
| `BusinessConditions` | `preferred_region: str \| None`, `deposit_budget: int \| None`, `monthly_rent_budget: int \| None`, `target_age: str \| None`, `operating_start_time: str \| None`, `operating_end_time: str \| None`, `priority_metrics: list[str]` |
| `RuntimeContext` | `user_id: str`, `session_id: str`, `user_role: str`; 신뢰 가능한 실행 계층에서 주입 |
| `UserPreferences` | `user_id: str`, `preferred_regions: list[str]`, `deposit_budget: int \| None`, `monthly_rent_budget: int \| None`, `target_customer: str \| None`, `priority_metrics: list[str]`, `shortlisted_areas: list[str]` |
| `StudySpotState` | `messages`, `business_conditions`, `searched_areas`, `current_candidates`, `tool_results`, `market_scores`, `missing_data`, `pending_action` |
| `MarketScore` | 아래 6개 세부 점수, `total_score: float`, `confidence: float`, `missing_data: list[str]` |
| `EvidenceItem` | `source: str`, `summary: str`, `is_mock: bool` |
| `AreaRecommendation` | `area_name: str`, 6개 세부 점수, `total_score: float`, `strengths: list[str]`, `risks: list[str]`, `evidence: list[EvidenceItem]`, `missing_data: list[str]`, `confidence: float` |
| `StudySpotResponse` | `status`, `recommendations: list[AreaRecommendation]`, `message: str`, `missing_required_inputs: list[str]`, `requires_approval: bool`, `approval_action` |

`RuntimeContext`는 신뢰 가능한 실행 계층에서 주입한다. 사용자 입력이나 LLM이 `user_id`·권한을 지정하게 하지 않는다.

### 반환 의미

| 상황 | success | is_mock | data / 오류 |
|---|---:|---:|---|
| 실제 조회 성공 | true | false | 검증한 정규화 payload, 오류 없음 |
| API 실패 후 Mock 사용 | true | true | 같은 payload 구조, 원래 오류 코드·Fallback 설명 유지 |
| 개발 Mock 모드 | true | true | 같은 payload 구조, source에 Mock 명시 |
| 재사용 가능한 실제 캐시 | true | false | 출처·조회 시점·캐시 사용 사실 보존; Mock 캐시는 true 유지 |
| 사용 가능한 결과 없음 | false | false | `{}` 또는 해당 Tool의 빈 목록, 오류 코드 제공 |

`success=True`는 실데이터 보장이 아니다. 빈 목록은 검색 결과 0건이라는 정상 결과일 수도 있다. 조회 실패와 구분한다. `data`가 넓은 타입이므로 각 Tool payload를 별도 모델로 선언·검증해야 한다.

공통 오류 코드: `API_TIMEOUT`, `API_AUTH_ERROR`, `API_RATE_LIMIT`, `API_BAD_REQUEST`, `API_RESPONSE_ERROR`, `AREA_NOT_FOUND`, `UNSUPPORTED_AREA`, `STATION_NOT_FOUND`, `NO_DATA`, `INVALID_INPUT`, `MISSING_REQUIRED_INPUT`, `TOOL_INTERNAL_ERROR`, `MAX_ITERATION_REACHED`. 추가 오류 코드는 역할 4와 합의한다. 민감한 원문 응답·키를 오류 메시지에 넣지 않는다.

### 응답 상태

| status | 의미·조건 |
|---|---|
| `success` | 분석 완료, 추천 1~3개. 점수와 근거 검증 통과 |
| `need_more_information` | 필수 조건 부족. `missing_required_inputs`와 질문 제공, 분석 데이터 Tool 미호출 |
| `no_result` | 검증 가능한 추천 없음. 빈 추천 목록과 원인·조건 완화안 제공 |
| `approval_required` | 외부 행동 실행 전 대기. `requires_approval=True`, 승인 대상 표시 |

`approval_action`은 `none`, `send_report`, `create_site_visit`. 승인 대기 외에는 false/none 조합을 사용한다. 시스템 오류 전용 status는 기존에 없으므로 **추가 제안:** 복구 불가 오류는 `no_result`에 오류 원인을 명시하고 State의 오류 코드를 보존한다. 후보 0개라는 업무 결과와 UI 설명을 구별한다.

## 4. 추가 제안: 데이터와 호출 인터페이스

이 절의 상세 타입·인자 순서는 skeleton PR에서 확정할 초안이다. API URL·공급자 파라미터를 뜻하지 않는다. HTTP 파라미터는 역할 1이 공식 문서로 확인한다.

공통 단위: 예산은 원(KRW), 반경은 m, 좌표는 위도·경도, 시각은 `HH:MM`, 날짜·조회 시점은 시간대 포함 ISO 형식. 지역·역 코드는 앞자리 0을 보존하는 문자열. 자정 통과 영업시간은 허용하고 시작=종료가 24시간인지는 별도 명시해야 한다.

| 제안 모델 | 필수 내용 |
|---|---|
| `AreaIdentity` | `commercial_area_id`, `administrative_code`, `area_name`, `latitude`, `longitude`; 모르는 코드는 생성하지 않음 |
| `AnalysisPeriod` | `start_date`, `end_date`, `timezone`, `day_types`, `start_time`, `end_time` |
| `MetricObservation` | `metric_name`, `value: float \| None`, `unit`, `period`, `source`, `is_mock`, `missing_reason`; 지표 누락과 0 분리 |
| `AcademyDemandData` | `commercial_area_id`, `administrative_code`, `observations: list[MetricObservation]`, `missing_data` |
| `NearbyStation` | `station_id`, `station_name`, `latitude`, `longitude`, `distance_m`; 코드 체계도 문서화 |
| `StationTrafficData` | `station_id`, `observations`, `missing_data`; 출구·시간대 구분 가능한 정보 포함, 집계 기준 고정 |
| `ScoringInput` | `area: AreaIdentity`, `conditions: BusinessConditions`, `period: AnalysisPeriod`, `tool_results: dict[str, ToolResult]` |

계약 이름: `get_academy_demand(area, target_age, period)`, `find_nearby_stations(latitude, longitude, radius_m)`, `get_station_exit_traffic(station_id, period)`, `calculate_market_score(scoring_input)` → 모두 `ToolResult`.

정상 `data`는 각각 AcademyDemandData의 직렬화 사전, NearbyStation의 직렬화 목록, StationTrafficData의 직렬화 사전, MarketScore의 직렬화 사전이다. DTO와 직렬화 결과를 혼용하지 않는다. 시간대별 비율과 통행 인원은 별개 지표이며 임의 변환하지 않는다.

나머지 고정 Tool 이름: `search_supported_districts`, `resolve_area_entities`, `get_district_congestion`, `get_visitor_demographics`, `search_competitors`, `get_rent_and_closure_data`, `save_user_preferences`, `save_shortlist`, `create_site_visit_event`, `send_analysis_report`.

### UI → Agent 추가 제안

`run_analysis(request: AgentRequest, context: RuntimeContext) -> StudySpotResponse`.

`AgentRequest`는 기존 입력 `messages`, `business_conditions`를 유지한다. 선택 필드 `approval_decision`은 승인/거절, `action_id`, 표시한 payload의 버전을 담는다. UI는 State 전체를 전달하거나 수정하지 않는다. 승인 동작도 같은 Agent 경계로 전달한다.

`pending_action`의 제안 타입 `PendingAction`: `action_id`, `action_type`, `payload_version`, `display_summary`, `status`, `user_id`, `session_id`. 실제 실행 payload는 서버 측 임시 보관하며 사용자에게 승인 전 내용을 표시한다. 상태는 pending/approved/rejected/executed/failed. 승인 사용자·내용 버전이 다르면 실행하지 않는다. 중복 클릭·재전송으로 중복 외부 행동이 발생하지 않게 한다.

State 상세 타입 제안: messages는 메시지 목록, searched_areas/current_candidates는 AreaIdentity 목록, tool_results는 호출 ID별 ToolResult 사전, market_scores는 상권 ID별 MarketScore 사전, missing_data는 문자열 목록, pending_action은 PendingAction 또는 None. 메시지 구체 타입·갱신 규칙은 역할 2·5가 선택한 LangChain 버전에 맞춰 확정한다.

## 5. 점수와 누락 정책

| 필드 | 최대점 |
|---|---:|
| `academy_demand_score` | 25 |
| `target_customer_score` | 20 |
| `station_traffic_score` | 15 |
| `activity_score` | 15 |
| `rent_score` | 15 |
| `competition_score` | 10 |

기존 합의: 총점 0~100, 세부 점수 합과 일치, confidence 0~1. 원천 데이터 누락을 0으로 채우지 않는다. 단, 기존 float 필드만으로는 '계산 불가'를 표시할 수 없어 아래 정책 선택이 필요하다.

**추가 제안:** 계산 불가 세부 점수는 `float | None`으로 확장하고 `missing_data`에 기록한다. 총점은 관측 가능한 세부 점수의 합이며 100점으로 재환산하지 않는다. 전 항목 누락 후보는 추천에서 제외한다. UI는 누락 항목을 '데이터 없음'으로 표시한다. 부분 데이터 후보는 비교 한계를 위험요인으로 표시한다. 이 nullable 변경은 역할 4가 먼저 모델 PR로 반영해야 하며 각자 임의 적용하지 않는다.

정규화 기준·임계값·반올림·confidence의 계산식은 기존 합의에 없으므로 역할 4가 수치 예제와 함께 확정한다. 사용자가 평가 우선순위를 바꿔도 기본 배점은 자동 변경하지 않는다. 가중치 변경 테스트는 승인된 별도 정책이 생긴 경우만 점수 변경을 검증하고, 그전에는 우선순위 설명·재분석 흐름을 검증한다.

## 6. Git·테스트·PR 공통 규칙

최초 clone 후 본인 기능 브랜치를 생성·push한다. 작업 시작 전 `main`을 pull하고 본인 브랜치에 merge한다. 커밋·push 후 PR을 열고 다른 조원 최소 1명 검토 후 merge한다. `main` 직접 push 금지. 같은 파일을 두 사람이 동시에 수정하지 않는다. 공통 파일 변경은 소유자에게 요청한다.

각 테스트는 ID, 초기 상태, 입력, 기대 Tool, 기대 status, 통과 조건을 기록한다. 테스트는 역할별 파일로 분리하며 공통 fixture 수정도 소유자를 정한다. 기본 테스트는 외부 호출 없이 Mock·가짜 모델로 재현 가능해야 한다.

- [ ] 담당 파일·공통 모델·Tool 이름 준수
- [ ] 입력/출력·오류·Mock 계약 준수
- [ ] 자체 테스트 실행 결과와 재현 방법 첨부
- [ ] 공통 계약 변경 시 이유·영향 모듈·변경 전후·이관 순서 기재
- [ ] 최신 main 반영, 타 담당 파일 변경 검토
- [ ] `.env`, API 키, 개인정보, `.streamlit/secrets.toml` 미포함
- [ ] 미구현·Mock·실 API 검증 여부 구분
- [ ] 다른 조원 1명 이상 검토
