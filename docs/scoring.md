## 0. 한눈에 보기

**이 점수는 "사용자 조건 기반 상권 적합도"입니다.** 창업 성공 확률이나 예상 매출이 아닙니다. 실제 매출·폐업 데이터로 학습한 모델이 아니므로 성공을 예측한다고 표현하지 않습니다.

```
데이터 Tool 조회 결과 (중우)
      ↓  Agent 코드가 ScoringInput으로 조립 (석휘)
calculate_market_score (효주)
  1. 항목별 원자료 꺼내기
  2. 기준값과 비교해 0~1로 바꾸기
  3. × 배점 → 세부 점수
  4. 합산 → 총점, 데이터 품질 → 신뢰도
      ↓
MarketScore → rank_market_scores로 순서 → AreaRecommendation 조립 (석휘) → 화면 (명하)
```

| 항목 (배점) | Tool | 원자료 | 좋은 방향 | 데이터 |
|---|---|---|---|---|
| 학원 수요 (25) | `get_academy_demand` | 타깃 학령 학원 상위 5개의 추정 통화 고객 수 합 | 많을수록 ↑ | 실데이터 |
| 타깃 방문자 (20) | `get_visitor_demographics` | 상권 방문자 중 타깃 연령대 비율 (남녀 합) | 높을수록 ↑ | 실데이터 |
| 지하철 통행 (15) | `get_station_exit_traffic` | 가까운 역의 하루 시간당 평균 출구 이용자 수 | 많을수록 ↑ | 실데이터 |
| 운영시간 유동성 (15) | `get_district_congestion` | 하루 상권 혼잡도 중 사용자 운영시간대 비중 | 높을수록 ↑ | 실데이터 |
| 임대료 (15) | `get_rent_and_closure_data` | 월세·보증금 총액 ÷ 사용자 예산 | 낮을수록 ↑ | Mock |
| 경쟁점포 (10) | `search_competitors` | 반경 500m 안 스터디카페 수 | 적을수록 ↑ | 실데이터 |

- 배점은 팀이 정한 **고정값**입니다. 사용자 우선순위로 바뀌지 않습니다.
- 총점 = 세부 점수 합. 데이터가 없는 항목은 `None`이고 총점에는 0점으로 들어갑니다.

## 1. 근거

근거를 세 층으로 나눕니다. **근거가 있는 것과 팀이 정한 가정을 섞지 않는 것**이 원칙입니다.

### 1-1. 왜 이 지표들을 쓰나 (근거 있음)
| 근거 | 내용 | 관련 항목 |
|---|---|---|
| 서울시 상권분석 서비스 (서울특별시, 서울신용보증재단 운영) | 점포수, 개업·폐업률, 생존율, 추정매출, 유동인구, 주거·직장인구, 임대시세를 상권 핵심 지표로 사용 | 유동인구(지하철·타깃·운영시간 유동성), 임대료, 경쟁점포 |
| 조영혜·이명훈 (2022), 「지하철역과 연계된 시설이 역사 내부 상업공간 임대료에 미치는 영향」, 한국콘텐츠학회논문지 22(1), doi:10.5392/JKCA.2022.22.01.261 | 회귀분석 결과 일일 승하차 인원이 상업공간 임대료에 영향을 줌 | 지하철 통행 |
| 소상공인시장진흥공단 상권정보시스템 | 경쟁 점포를 반경 기준으로 분석하고 경쟁 수준을 단계로 제공 | 경쟁점포 |

### 1-2. 왜 이렇게 계산하나 (근거 있음)
OECD·EU JRC, *Handbook on Constructing Composite Indicators: Methodology and User Guide* (2008, ISBN 978-92-64-04345-9)를 따릅니다.

| 우리 설계 | 핸드북 |
|---|---|
| 기준값에 대한 **배율**로 정규화 | 5.4절 *Distance to a reference* (85쪽): 기준값에 대한 비율로 정규화 |
| 기준값을 최댓값·최솟값이 아니라 **중앙값**으로 | 28쪽: Min-Max는 극단값·이상치가 결과를 왜곡할 수 있음 |
| 100점을 6개 항목에 배분 | 6.5절 *Budget Allocation Process* (96쪽): 경험과 판단으로 100점을 지표에 배분 |
| 배점을 "정답"이라 하지 않음 | 31쪽: 가중치는 본질적으로 가치 판단(value judgement) |
| 민감도 분석 수행 | 핸드북 전반: 가중치·방법을 바꿔 결과의 견고성을 확인하도록 권고 |

### 1-3. 팀이 정한 가정값 (근거 없음 → 민감도 분석으로 확인)
| 가정값 | 사용처 | 코드 상수 |
|---|---|---|
| 배점 25·20·15·15·15·10 | 전체 (1-2의 배분 방식으로 정함) | `models/schemas.py` `SCORE_MAX_POINTS` |
| 배율 0.5배 → 0점, 1.5배 → 만점 | 학원·타깃·지하철·운영시간 유동성 | `RATIO_ZERO`, `RATIO_FULL` |
| 예산 대비 80% 이하 만점, 120% 이상 0점 | 임대료 | `RENT_FULL`, `RENT_ZERO` |
| 경쟁 반경 500m, 10개 이상 0점 | 경쟁점포 | `COMPETITION_RADIUS_M`, `COMPETITION_ZERO_COUNT` |
| 데이터 품질 계수 1.0 / 0.5 / 0 | 신뢰도 | `QUALITY_REAL`, `QUALITY_MOCK` |

숫자를 바꾸려면 **이 문서, 코드 상수, 테스트 기대값을 같이** 고치고 정책 버전을 올립니다.

### 1-4. 확인하지 못한 것
- 스터디카페 입지에 특화된 학술 연구는 찾지 못했습니다.
- 이전에 AI가 제시한 연구(평촌 학원가, 캠퍼스 상권 등)는 원문을 확인하지 못해 **인용하지 않습니다.**

## 2. 공통 규칙

### 2-1. 정규화: 기준값 대비 배율
학원·타깃·지하철·운영시간 유동성 4개 항목에 씁니다.

```
배율 r = 이 상권 값 ÷ 기준값
정규화 n = (r − 0.5) ÷ (1.5 − 0.5), 0~1로 자름
세부 점수 = n × 배점
```

| 배율 | 정규화 | 의미 |
|---|---|---|
| 0.5 이하 | 0 | 기준의 절반 이하 |
| 1.0 | 0.5 | 기준 수준 → 배점의 절반 |
| 1.5 이상 | 1 | 기준의 1.5배 이상 → 만점 |

**기준값** = 서비스가 지원하는 상권 5~10곳의 값의 **중앙값**. 한 번 계산해서 스냅샷으로 **고정**합니다(5절).

**후보끼리 비교하는 방식(후보 집합 상대 정규화)을 쓰지 않는 이유**
| | 후보 집합 상대 정규화 | 고정 기준값 (채택) |
|---|---|---|
| 후보가 바뀌면 | 같은 상권의 점수가 달라짐 | 점수 그대로 |
| 같은 입력 반복 (SCR-02) | 후보 구성에 따라 달라질 수 있음 | 항상 같음 |
| 후보가 1~2곳일 때 | 최고·최저가 억지로 만점·0점이 됨 | 문제 없음 |

**기준값이 0이거나 없으면** 배율을 계산할 수 없으므로 해당 항목은 `None`, 사유 "기준값 없음"입니다.

### 2-2. 누락과 실제 0
| 상황 | 처리 |
|---|---|
| 실제 0 (예: 반경 안 경쟁점포 0개) | 값 0으로 계산 |
| 데이터 없음 (조회 결과 없음, 조회 실패, 빈 응답) | 세부 점수 `None`, `missing_data`에 사유 기록, 총점에는 0점 |
| 학원 API `stat=[]` | 0개인지 표본 부족인지 알 수 없으므로 **누락**으로 처리 |
| 전 항목 누락 | 신뢰도 0, `rank_market_scores`가 추천 후보에서 제외 |
| 일부 누락 | 추천 가능. 비교 한계를 `risks`에 기록 (조립은 역할 5) |

- 실패한 `ToolResult`의 빈 `data`를 0으로 계산하지 않습니다.
- `missing_data` 형식: `"세부 점수 이름: 사유"` (예: `"competition_score: search_competitors 조회 실패 (API_TIMEOUT)"`).
- 점수가 있어도 일부만 반영한 경우(예: 보증금 없이 월세만) 사유를 기록합니다.

### 2-3. 불일치 처리
| 상황 | 처리 |
|---|---|
| 다른 상권의 조회 결과가 섞임 (`commercial_area_id` 불일치) | 계산 전체 거절, `INVALID_INPUT` |
| 입력 형식 오류, 필수 조건 부족 | 계산 전체 거절, `INVALID_INPUT` |
| 단위가 예상과 다름 | 해당 항목 `None`, 사유 "단위 불일치" |
| 시간대별 데이터(지하철·혼잡도)의 날짜가 분석 기간 밖 | 해당 항목 `None`, 사유 "기간 불일치" |
| 분석 기간에 시각이 지정됨 (하루 전체가 아님) | 지하철·운영시간 유동성 `None`, 사유 "하루 전체 데이터 필요" |
| 음수, 비율 100% 초과 등 불가능한 값 | 해당 항목 `None`, 사유 "데이터 오류" |

- 학원·방문자 API는 요청 기간이 아니라 API가 주는 **통계 기간**(`statStartDate~statEndDate`)을 그대로 씁니다. 최신 통계만 제공되므로 기간 불일치로 보지 않습니다.
- 지하철·혼잡도 Tool은 `period`에 시각이 있으면 그 시간대만 돌려줍니다. 운영시간 비중을 계산하려면 하루 전체가 필요하므로 **시각 없이 조회**해야 합니다.

### 2-4. Mock 전파
- 계산에 Mock이 **하나라도** 쓰이면 `calculate_market_score`의 `ToolResult.is_mock = True`.
  - Tool 결과의 `is_mock`, 관측값 하나하나의 `is_mock`, API 실패 후 Mock 대체(성공 + `error_code` 유지)를 모두 봅니다.
  - **기준값 스냅샷이 Mock**이면 그 기준값을 쓴 결과도 `is_mock = True`입니다. 신뢰도는 데이터 품질만 반영하므로 따로 낮추지 않습니다.
- 어느 항목이 Mock인지는 근거(`EvidenceItem.is_mock`)에 항목별로 표시합니다 (역할 5).

### 2-5. 신뢰도 (confidence)
**의미**: 이 점수가 **얼마나 실제 데이터에 기반했는지**를 나타내는 데이터 품질 지표입니다. 추천 상권의 성공 확률이 아닙니다.

```
신뢰도 = Σ(항목 배점 × 데이터 품질) ÷ 100
```

| 데이터 품질 | 계수 |
|---|---|
| 실데이터 | 1.0 |
| Mock (개발 Mock, 실패 후 Mock, 임대료 Mock) | 0.5 |
| 누락 (`None`) | 0 |

- 한 항목에 관측값이 여러 개 쓰이면 하나라도 Mock일 때 그 항목을 Mock으로 봅니다.
- 타깃이 "전체"면 조회 없이 정해지는 값이라 품질 1.0입니다 (3-2).
- 데이터 최신성은 v1에서 반영하지 않습니다 (7절 한계).

### 2-6. 반올림
| 값 | 규칙 |
|---|---|
| 세부 점수 | 소수 1자리, 사사오입 (`Decimal`, `ROUND_HALF_UP`) |
| 총점 | **반올림한 세부 점수의 합** (합과 총점이 항상 일치) |
| 신뢰도 | 소수 2자리, 사사오입 |

Python 기본 `round()`는 쓰지 않습니다. 두 가지 문제가 있습니다.
- 부동소수 오차: 0.825는 실제로 0.82499…로 저장되어 `round(0.825, 2)` = 0.82
- 짝수 쪽 반올림: `round(0.125, 2)` = 0.12, `round(2.5)` = 2

그래서 **`Decimal(str(값))`**으로 바꾸고, 계산 오차(예: 7.4999999999)를 **소수 9자리에서 먼저 정리**한 뒤 `ROUND_HALF_UP`으로 반올림합니다. 예: 12.249999999999998 → 12.25 → **12.3** (`round()`는 12.2).

### 2-7. 동점 정렬 (`rank_market_scores`)
총점 높은 순 → 신뢰도 높은 순 → `commercial_area_id` 오름차순. 전 항목 누락 후보는 뺍니다.

## 3. 항목별 산식

### 타깃 연령 연결표 (결정, `TARGET_AGE_MAPPING`)
화면 선택지는 명하님 `TARGET_AGE_OPTIONS`와 같습니다.

| 화면 선택지 | 학원 `target_age` (school_age) | 방문자 `target_age` (age_group) |
|---|---|---|
| 중학생 | middle | 10 |
| 고등학생 | high | 10 |
| 대학생 | univ | 20 |
| 20대 | univ | 20 |
| 30대 이상 | all | 30 |
| 전체 | all | 조회 안 함 |

표에 없는 값이 오면 학원·타깃 항목은 `None`, 사유 "지원하지 않는 타깃 연령"입니다.

### 3-1. 학원 수요 (25점)
| 항목 | 내용 |
|---|---|
| Tool | `get_academy_demand(area, target_age=school_age, period)` |
| 지표 | `estimated_academy_call_customers`, 단위 `persons`, 원천 `stat[].count` |
| 원자료 | 타깃 학령 학원 상위 5개의 추정 통화 고객 수 **합** |
| 좋은 방향 | 많을수록 ↑ |
| 기준값 | 스냅샷의 같은 학령 합의 중앙값 |
| 계산 | 2-1 공통 공식 |
| 이상치 | 1.5배 이상은 만점으로 잘림 → 한 학원이 튀어도 점수 상한 유지 |
| 누락 | `stat=[]`, 조회 실패, 단위 불일치 → `None` |

⚠️ **학원 수가 아닙니다.** API는 전체 학원 목록이 아니라 통화량 기준 상위 5개만 줍니다.

**예제**: 합 1,200명, 기준값 1,000명 → 배율 1.2 → 정규화 0.7 → **17.5점**

### 3-2. 타깃 방문자 (20점)
| 항목 | 내용 |
|---|---|
| Tool | `get_visitor_demographics(area, target_age=age_group, period)` |
| 지표 | `visitor_age_group_rate`, 단위 `percent` (남성·여성 각각) |
| 원자료 | 상권 방문자 중 타깃 연령대 비율 = **남성 비율 + 여성 비율** |
| 좋은 방향 | 높을수록 ↑ |
| 기준값 | 스냅샷의 같은 연령대 비율의 중앙값 |
| 계산 | 2-1 공통 공식 |
| 누락 | 조회 실패, 비율 없음, 응답의 연령대가 요청과 다름("연령대 불일치") → `None` |

- 이 데이터는 해당 상권에 10분 이상 머문 SK텔레콤 회선 사용자 통계입니다 (중우님 문서).
- 타깃이 "전체"면 조회하지 않고 모든 후보가 **10점**(배율 1.0과 같음)이라 순위에 영향이 없습니다.
- v0.4까지는 지하철 연령별 조회를 쓰려 했지만, 중우님이 방문자 연령 Tool을 구현해서 바꿨습니다. 역 하나가 아니라 **상권 자체**의 방문자라 더 직접적입니다.

**예제**: 남 14% + 여 16% = 30%, 기준값 20% → 배율 1.5 → 정규화 1.0 → **20.0점**

### 3-3. 지하철 통행 (15점)
| 항목 | 내용 |
|---|---|
| Tool | `find_nearby_stations` → `get_station_exit_traffic(station_id, period)` (**하루 전체** 조회) |
| 대상 역 | 반경 안 역 중 **가장 가까운 1개** (중복 반영·호출 증가 방지) |
| 지표 | `station_exit_user_count`, 단위 `persons/hour`, 출구별·1시간 단위 |
| 원자료 | 시간대별로 모든 출구 이용자를 더한 뒤, **데이터가 있는 시간대 수로 나눈 평균** |
| 좋은 방향 | 많을수록 ↑ |
| 기준값 | 스냅샷의 상권별 시간당 평균의 중앙값 |
| 누락 | 역 없음, 데이터 없음, 분석 기간에 시각 지정 → `None` |

- 지하철이 다니지 않는 새벽 시간대는 데이터가 없으므로 "운행 시간대 평균"이 됩니다. 기준값도 같은 방식으로 만듭니다.
- 이 항목은 역의 **규모**만 봅니다. 시간대는 3-4에서 봅니다.

**예제**: 20개 시간대 × (1번 출구 250명 + 2번 출구 150명) → 시간당 400명, 기준값 500명 → 배율 0.8 → 정규화 0.3 → **4.5점**

### 3-4. 운영시간 유동성 (15점, 필드 `activity_score`)
| 항목 | 내용 |
|---|---|
| Tool | `get_district_congestion(area, period)` (**하루 전체** 조회) |
| 지표 | `district_congestion_density`, 단위 `persons/m2` (시간대별) |
| 원자료 | **사용자 운영시간대 혼잡도 합 ÷ 하루 전체 혼잡도 합** |
| 좋은 방향 | 높을수록 ↑ (내 영업시간에 사람이 몰리는 상권일수록) |
| 기준값 | 스냅샷의 상권별 24시간 혼잡도로 **같은 운영시간대 비중**을 구한 뒤 중앙값 |
| 계산 | 2-1 공통 공식 |
| 누락 | 데이터 없음, 하루 전체 혼잡도 0, 분석 기간에 시각 지정 → `None` |

- 운영시간에 포함되는 시간대: 시간대 **시작 시각**이 운영시간 안에 있으면 포함합니다 (예: 09:00~23:00 → 9시~22시, 14개).
- 자정을 넘으면(예: 18:00~02:00) 같은 날 0~1시 데이터로 새벽 시간대를 대신합니다 (하루 단위 조회라서).
- 시작=종료(24시간 운영)면 비중이 모두 100% → 모든 후보 7.5점이라 순위에 영향이 없습니다.
- 레벨 지표(`district_congestion_level`, 1~10단계)는 더할 수 없는 단계값이라 쓰지 않습니다.
- 기준이 **사용자가 입력한 운영시간**이라 외부 통계 근거가 필요 없습니다.

**설계서의 "저녁·주말 활성도"에서 바꾼 이유** (2026-09-11 결정)
- 팀 설계서에 "저녁·주말"을 고른 이유가 적혀 있지 않습니다.
- 찾은 자료는 오히려 스터디카페가 "오전부터 야간까지 고르게 이용"된다고 합니다 (작심스터디카페 운영 데이터, Businesskorea 2026-01-20).
- 설계서(docx) Tool 표에서 혼잡도 조회 시간 범위를 **"State의 운영시간"**에서 가져오도록 되어 있어, 운영시간 기준은 원래 설계 방향과 같습니다.
- v0.3~0.4에서는 혼잡도 데이터가 없어 지하철 시간대 데이터를 쓰려 했지만, 중우님이 혼잡도 Tool을 구현해서 **원래 설계서대로 혼잡도**를 씁니다 (v0.5). 역 하나가 50점에 영향을 주던 문제도 줄었습니다.
- 필드 이름 `activity_score`와 배점 15점은 그대로입니다. 주말은 v2로 미룹니다.

**예제**: 9~22시 밀도 0.20, 나머지 10개 시간대 0.07 → 2.8 ÷ 3.5 = 80%, 기준값 80% → 배율 1.0 → 정규화 0.5 → **7.5점**

### 3-5. 임대료 적합성 (15점)
| 항목 | 내용 |
|---|---|
| Tool | `get_rent_and_closure_data(area, period)` (현재 **Mock**) |
| 지표 | `monthly_rent_krw` (월세 총액, `KRW/month`), `deposit_krw` (보증금 총액, `KRW`) |
| 비교 기준 | 사용자 `monthly_rent_budget`, `deposit_budget` |
| 좋은 방향 | 예산 대비 낮을수록 ↑ |
| 계산 | 월세·보증금 각각 비율 r = 금액 ÷ 예산, n = (1.2 − r) ÷ (1.2 − 0.8), 0~1로 자름. **둘 중 낮은 n** (더 부담되는 쪽)을 씀 |
| 누락 | 둘 다 없음 → `None`. 하나만 있으면 그것만 반영하고 사유 기록 |

| 예산 대비 | 점수 |
|---|---|
| 80% 이하 | 15점 |
| 100% | 7.5점 |
| 120% 이상 | 0점 |

- **면적은 쓰지 않습니다** (2026-09-11 결정). 면적 API가 없고, 중우님 Mock 값이 이미 **총액**이라 바로 예산과 비교합니다.
- **보증금**: 중우님 Tool에 보증금 총액이 있어서 v0.5부터 평가합니다. 월세와 보증금을 따로 비교하고 더 부담되는 쪽을 쓰므로, 두 값 사이의 추가 가중치가 필요 없습니다.
- 예산 0: 금액도 0이면 만점, 아니면 0점.
- **예산 초과 표시**: `rent_score`가 7.5점 미만이면 월세·보증금 중 하나 이상이 예산을 넘은 것입니다. 역할 5가 이 기준으로 `risks`에 "예산 초과" 문장을 씁니다 (공통 모델에 칸을 추가하지 않음).
- **폐업률**(`closure_rate_percent`)은 배점 항목이 없어 점수에 넣지 않습니다. 역할 5가 위험요인 문장에 쓸 수 있습니다 (8절).

**예제**: 월세 300만 ÷ 300만 = 100% → 0.5, 보증금 2,000만 ÷ 3,000만 = 67% → 1.0 → 낮은 쪽 0.5 → **7.5점**

### 3-6. 경쟁점포 포화도 (10점)
| 항목 | 내용 |
|---|---|
| Tool | `search_competitors(area, radius_m=500)` (TMAP 장소 검색, 실데이터) |
| 원자료 | 반경 500m 안 "스터디카페" 검색 결과 수 = `len(competitors)` (조회 시점 기준) |
| 좋은 방향 | 적을수록 ↑ |
| 계산 | n = 1 − (점포 수 ÷ 10), 0~1로 자름 |
| 누락 | 조회 실패, 좌표 없음, 반경이 500m가 아님 → `None` (0개와 구분) |

- "경쟁점포가 많으면 수요가 검증된 지역일 수 있다"는 해석은 점수에 넣지 않고, 역할 5가 `strengths`·`risks` 문장으로 표현합니다.

**예제**: 3개 → 정규화 0.7 → **7.0점**

## 7. 한계
- 학원 데이터는 **상위 5개 학원**만 반영합니다.
- 방문자 연령 비율은 **SK텔레콤 회선 사용자** 통계입니다. "30대 이상"은 30대 비율만 봅니다.
- 주말 유동성은 v1에서 반영하지 않습니다 (하루 단위 조회).
- 임대료는 **Mock**, 기준값 스냅샷도 **Mock**입니다.
- 면적을 반영하지 않습니다. 같은 월세라도 매장 크기가 다를 수 있습니다.
- 데이터 최신성은 신뢰도에 반영하지 않습니다.
- 스터디카페 특화 선행연구가 없어, 지표 선택은 일반 상권 분석 지표를 적용한 것입니다.
- 점수는 적합도이며 **성공 확률이 아닙니다.**
